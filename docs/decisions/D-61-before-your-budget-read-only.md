# D-61: "Before your budget" rows are read-only and stay out of Activity and Payees (Nov 4, 2026)

**Decided by the owner.** Posted rows dated before an account's budget start ("history", `isHistory` in `apps/worker/src/views/rows.ts`) never enter the budget, but the app still let you edit them like any other row, and they could show on Activity's first month. The owner asked whether to hide them, make them read-only, or delete them. Deleting was ruled out: the budget already skips them, Reports and net worth add them up, the drift check uses them, and with no off-site backups (D-29) and Plaid's 10-link limit a delete couldn't be undone. An adversarial review of the plan found the choices below; the owner picked each one.

1. **Read-only.** The transaction sheet for one of these rows has kind `history`: a "Not counted" note, what the bank says, its category if it already had one, and its note, with Done and nothing to change (`apps/web/src/screens/TxnHistory.tsx`). The server refuses every edit to one with 409 `history`: `PATCH /transactions/:key` (category, Ready to Assign, split, note, estimate, won't clear, budget month, payee name, Owed to you) and `POST /transactions/categorize` (`refuseHistory` in `apps/worker/src/routes/transactions.ts`). The phone runs the same routes, so an offline edit is refused there too.
2. **No Owed to you on them.** Marking one as owed to you is refused with the rest. A payback that arrives later is handled like any other inflow (Waiting to match, then income or a match to another owed item). Marks already on such a row stay as they were.
3. **No learning from them.** Payee learning (the picker's "You've used for…" and the Always offer) reads only categories you set by hand, so these rows no longer feed it. This replaces "used for payee learning" in `docs/design.md` Budget start and the CSV history import's "payee learning".
4. **Out of Activity's lists.** Activity's month view and its plain list leave them out, in SQL before the page limit so paging is unchanged (`IN_BUDGET` in `apps/worker/src/routes/activity.ts`). A search still finds them, and the account's register still shows them, with the "Before your budget" badge.
5. **Out of Settings → Payees.** A payee whose every row is before the budget isn't listed and isn't offered in merge suggestions (`apps/worker/src/routes/settings/payees.ts`). The payee stays in the database, so if it comes back its name and merges are kept.

Nothing about how money is counted changes: the budget, Ready to Assign and account balances skipped these rows before and still do. `budget_from` is set once when an account is added and the budget start is set once, so a row can't move between history and the budget.
