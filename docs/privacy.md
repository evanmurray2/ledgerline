# Privacy design: a server that holds no key to a budget

Status: v6, Nov 10, 2026. A proposal: nothing here is built. The owner's decisions of Nov 10 (D-85) are part of the design. Three pairs of adversarial reviewers have attacked it (v1, v4, v5); this version includes their fixes, and section 15 lists what they found. The owner answered the four questions about how bank rows are filed (section 14.2, D-86). The last two questions were answered on Nov 10 (section 14.4, D-85, D-87). Nothing is open, and the build has started in the order of section 10. `docs/architecture.md` says what runs today.

What the owner asked: to offer Ledgerline to other people as a privacy-focused budget app, with the strongest privacy and security claims that can be made honestly, and to know what has to change and what users would see.

## 0. The short answer

Today the server stores every budget as plain text, so the honest claim is "we don't look". This design changes that to "we hold no key":

1. **The budget is encrypted on the device** with a key the server never has. The server stores only sealed data.
2. **All work on budget data moves to the device**: every edit, bank processing, matching, the daily scan. The device already works out every screen (D-45, D-46), but most edits and all bank work still run on the server, so this is a large move.
3. **The server still fetches bank data from Plaid in the background, as today, but seals each run at once** with a key only the person's devices hold, and keeps nothing readable from it. It keeps the key to each bank link, so it can fetch, repair and remove a link.
4. **No outside script runs where the keys are**, no email address is asked for, and logs hold nothing about a person.
5. **The code is public** and each release can be compared with it.

Limits that stay whatever is built (section 4): Plaid sees bank data; a web app runs the code its server sends; the server sees that an account exists and when it is used; the server can lie about bank data and the time; and the server could fetch a person's bank data again, because it holds the bank key.

What it costs:

- **Nobody can reset an account, and nothing can be restored** (accepted, D-85). A person who loses every passkey and the recovery key loses the budget. If the server ever lost part of a budget, the devices would keep a copy that can be read and exported but not sent back (5.3).
- **An account not opened for 24 months is deleted** (accepted, D-85).
- **Bank matching moves from the server to the device, and with it four changes to when and in what order bank rows are filed** (accepted, D-86; section 14.2). The largest: transfers between two banks pair by themselves more often than today.

### 1.2 What must never be said

- **"We can't read your data"**, **"what we store can't be read"** or **"nobody who breaks in can read it"**, flat. Someone who can change the code the server sends or runs can read it (4.2), we store readable account records (4.3), and we could fetch bank data again. Say "we hold no key to your budget" and "no readable copy".
- **"We keep nothing readable."** We keep account records, bank link ids, times and sizes (4.3).
- **"Zero-knowledge"** or **"end-to-end encrypted"**, for any budget.
- **"We have no access to your bank"** or **"we don't store your bank key"**.
- **"We keep no copy of your bank data."** We keep a sealed copy.
- **"Only you can see your transactions."** Plaid can, the bank can, and Cloudflare, as the platform, could see bank data as it passes through the Worker.
- **"Deleted at once", "gone for ever".**
- **"We can't be forced to hand anything over."** We can be made to hand over sealed data and account records, to fetch a person's bank data from Plaid, and in principle to ship changed code.
- **"Anonymous."** Cloudflare sees IP addresses, and Plaid knows who the person is.
- "Safe from quantum computers" (5.2), "audited", "bank-level", "military-grade", "unhackable".

### 1.3 The pitch that survives a hostile reader

> Your budget is encrypted on your devices with a key we never hold. Bank data comes through Plaid; we seal it the moment it arrives and keep no readable copy. We do keep the key to your bank link, so that we can fetch for you. No email, no trackers, public code. Like every web app, this depends on the code we send your browser; that code is public.

The parts about what the server does are our word (1.1); the pitch is not used in a place where that can't be said too.

## 4. Limits no design here removes

### 4.1 Plaid sees the bank data

Plaid fetches transactions from the bank and keeps them under its own policy. Its API answers only a server that holds our Plaid secret, so the data must pass through our Worker; Plaid can't encrypt to a person's device. The claims are therefore about what we **store**. The privacy policy names Plaid and links its policy and its page where a person can see and remove connections.

**A person who is locked out** (every passkey and the recovery key lost) can't sign in to remove a bank link. The server stops fetching for an account nobody opens after 90 days (5.5), and deletes it and its links at 24 months. Until then the link exists at Plaid; the policy says so and points to Plaid's page, where the person can remove it themselves.

A budget with no bank link has none of this. "Accounts without a bank link" (`docs/build-plan.md`) would be the most private mode; it needs the owner's Money-rules answers about starting balances and is not part of this design.

### 4.2 A web app runs whatever its server sends

The keys live in the browser, and the browser runs the JavaScript the Worker serves on each visit. Whoever controls that JavaScript can read the keys. A service worker can't prevent it: the browser replaces a service worker with whatever new one the server sends. A changed Worker can also keep the bank data it fetches before sealing it. No web-only design closes this. What can be done:

- make every release public and comparable (5.9), so an untargeted bad release leaves evidence. Code sent once to one person leaves none;
- make it hard to ship code without the owner seeing it (5.10);
- or ship an app from an app store, where the code is signed and can't change per visit. That has a yearly fee and breaks the $0 rule.

### 4.3 What the server and the operator still learn

- That an account exists, when it was made and last used, how many passkeys and devices it has, their names if the person gave any, each passkey's maker id, and each session's user agent.
- When the app is used and from which IP address (Cloudflare sees it; the app stores none).
- How many changes are made and when, and their rough size. Padding (5.3) blurs size, not count or timing; a bank run looks different from a typed edit.
- For each bank link: the Plaid Item id, the access token, **which bank it is** (Plaid's dashboard shows the operator every Item's bank), when it was linked, when Plaid says it has news or needs repair, when each run arrived, how many rows it added, changed and removed, and its size.
- Bank data, in the Worker's memory, between Plaid's answer and the seal. Cloudflare runs the Worker, so Cloudflare could see it there too.

The page "what we can hand over" (section 11) lists exactly this, and says plainly that the server could be made to fetch a person's bank data from Plaid.

### 4.4 The server can lie about bank data and the time

Plaid doesn't sign its answers for the device. A Worker running changed code could add, alter or drop bank rows and balances before sealing them, and the device would file them as true. The server also states when each run arrived, and supplies "today", which decides the current month. The bounds are the device's own, and they are wide:

- A run's time must be later than the run before it and not later than the device's clock (with 10 minutes' tolerance). After a quiet week, that window is a week wide: a lying server could place a row's arrival anywhere in it, which is enough to move a row across D-67's or D-68's lines.
- A device refuses a server "today" more than 24 hours from its own clock.
- A device whose own clock is wrong would see true runs as "in the future". It says "Check this device's date and time" and files nothing until it is fixed.

The server also checks each entry's time against its own clock, but that only catches a broken client; it is no protection against the server itself. This is the same trust as 4.2.

### 4.5 The device

Someone with the unlocked device and its passcode reads the budget, as today (`docs/phone-budget.md` 13.6). A jailbroken device, a malicious browser extension on a computer, a shared or exported passkey, and the iOS keyboard's learning are outside what the app controls.

## 5. Design

### 5.1 Shape

```
   Plaid ──(bank data, TLS)──▶ Worker: fetch step ──check, seal, sign──▶ sealed inbox ──▶ device
                                  (bank keys, cursors)                                       │
                                                                                 engine: all budget work
                                                                                 (edits, matching, scans)
   Directory: accounts, passkeys, sessions, usage counts                                     │
   BudgetStore: a sealed log (with the key slots), sealed    ◀────(sealed, signed entries)───┘
                snapshots, the sealed inbox, bank links
```

The server keeps doing five things: sign-in; fetching from Plaid and sealing; storing and ordering sealed entries; counting usage for the free plan's limits; deleting accounts. It stops doing everything that reads a budget.

### 5.2 Keys

Building blocks: AES-256-GCM, HKDF-SHA-256, HMAC-SHA-256, SHA-256, Ed25519 and X25519 from WebCrypto, which Safari 17 and Workers have. (Chrome and Firefox got X25519 and Ed25519 only in recent versions; an older desktop browser shows "This device can't open an encrypted budget". Phase 0 fixes the lowest versions.) Sealing to a public key uses HPKE base mode (RFC 9180) with X25519, HKDF-SHA-256 and AES-256-GCM. That is a short composition of WebCrypto calls; whether it is our own code checked against the RFC's test vectors or a small library is decided in phase 2 under the owner's review (5.10), since no paid reviewer exists. `docs/privacy-keys.md` is the appendix that fixes every derivation label, associated-data string, nonce rule and byte layout, and what each side checks; it was reviewed in its own right, and the key code follows it exactly. The rules it must hold:

- **Budget key.** 256 random bits made on the device when the budget is made, and only then: **a client never makes a key for a budget that already exists**, whatever the server says, so a server can't trick a device into starting over in the clear. (The one exception is the owner's budget at the cutover, section 8.) HKDF derives one key per use and per key version: log entries, snapshots, the inbox private key's wrap, and a signing key pair.
- **In memory.** Keys are non-extractable once imported. Seeds for the signing and slot key pairs pass through JavaScript as bytes for a moment (WebCrypto can't derive those key types directly) and are zeroed after import. The raw budget key is unwrapped as extractable only during a key change, which needs a fresh passkey prompt. The key kept for a page refresh (`holdKey` in `vault.ts`) holds derived keys only.
- **Key slots are public-key slots.** Each way in has an X25519 key pair derived from a secret only that way in can produce:
  - **one per passkey**, derived from that passkey's PRF output (the WebAuthn `prf` extension the copy already uses). Sign-in uses discoverable passkeys, so the app can't know which passkey will answer before it asks: the PRF input for slots is one constant for the whole app, sent as the first input in `eval`; the copy's per-device salt is the second. The labels differ from the copy vault's, so the two uses of one passkey give unrelated keys.
  - **one for the recovery key** (5.8).
  - The public halves are recorded in the log, in signed entries, **sealed under the budget key**: the device doing a key change holds that key, and each way in can derive its own pair, so the server never sees a slot's public half. The budget key is sealed (HPKE) to each public half.
  - **Each slot carries its own check.** HPKE proves nothing about who sealed: anyone who knew a slot's public half could seal a budget key of their choosing to it and hand a new device a false budget. So when a way in is created, the device that holds its secret also writes a MAC, keyed from that secret (the PRF output or the recovery key), over the budget id and the budget's first signing public key. A new device, or a recovery sign-in, checks that MAC first, then follows the chain of key-change entries from that first signing key to the current one, each signed by the key before it and naming the log's position, and only then trusts what it unseals.
  - Why public-key: a key change must wrap the new budget key for **every other** passkey and for the recovery key, and the device doing it holds neither their PRF outputs nor the recovery key. With symmetric slots, removing one passkey would lock out all the others.
- **The slots live in the log, in `BudgetStore`**, not in the Directory. A key change is one log entry that holds the new budget key sealed to every remaining slot, the budget key it replaces and the old inbox private key, both wrapped under the new budget key (so a device that joins later can still read what was sealed before, and waiting bank runs can still be opened), the new signing and inbox public keys, and the log's position, and is signed with the old signing key. It is appended in one transaction or not at all, so a phone killed halfway leaves the old key in force. A test kills the change at every step.
- **Sign-up ends only after the new slot has been opened once**, with a second passkey prompt (PRF output is often missing from the answer to creating a passkey), so a passkey that can't give PRF output is found before a budget depends on it. Settings checks from time to time that the recovery slot still matches the current key version.
- **A passkey with no PRF can't open a budget.** Today such a passkey opens the budget in memory (D-57 item 4). iCloud passkeys on iOS 18 and later have PRF; older systems don't. Other passkey apps and security keys vary: phase 0 tests them, and that two PRF inputs work with an iCloud passkey.
- **Signing.** An Ed25519 pair derived from the budget key. The server holds the public half and refuses any entry or snapshot not signed by it, so a session that holds no key (a stolen cookie, a passkey with no PRF) can't write junk into a budget.
- **Inbox key pair.** An X25519 pair made on the device. The private half is sealed under the budget key and travels in the log; the public half goes to the server. The server seals bank runs to it (5.5).
- **What the Worker vouches for.** The server takes a signing or inbox public key only in a request with a recent passkey check, signed by the current signing key, and stores it with an HMAC made with a Worker secret over the budget, the key version and the key. The fetch step and the append path refuse a key whose HMAC doesn't match. This stops a database writer from inventing a key. It does not stop them from putting back an older key with its older HMAC; every signed run manifest therefore names the inbox key it was sealed to, and a device refuses a run sealed to any key but the current one (5.5).
- **Changing the key.** Removing a passkey or making a new recovery key makes a new key version. (Signing a device out does not: a device that shares an iCloud passkey would get the new key again, so it would protect nothing. Signing out works as today, by the server's per-device share, plus a signed entry, 5.3.) Every entry and every sealed run names its key version, and the server refuses entries under an old version once the key-change entry is stored. A key change is never blocked by a waiting bank run or by the breaker (5.3). Entries written before stay readable to whoever held the old key and an old copy of the data; the policy says so.
- **One way in can take the whole budget.** Anyone who holds one passkey, or the recovery key, holds the budget key, and so could write a key change that drops every other way in; with no reset, the real owner would be locked out for good. To blunt this (D-89), the server holds back for 7 days **every** key change that is made from a recovery-key sign-in or from a passkey added in the last 7 days, shows a notice on the other devices, and lets any way in that is still listed cancel it. It is every key change, not only one that removes a way in, because the server can't see into a way in's sealed record: a key change that keeps a way in by name can still lock it out. So the notice says "a key change is planned", not only which way in goes. Every device also shows a notice for a passkey or recovery key that another device added: without it, a thief with the recovery key could add a passkey, wait 7 days in silence, and then be an old way in. A thief who also controls the server isn't stopped. The policy says to guard the recovery key like the budget itself.
- **A removed way in and a dishonest server together** can show a device that has not yet seen the real key change a false one. Revocation is certain only for devices that have seen the change.
- **The copy on the device stays as built**: its own data key, wrapped under the passkey's PRF output and the per-device server share, so "Sign out other devices" still turns a copy off. The wrapped budget key is kept in that vault too.
- **Adding a device.** A passkey synced by iCloud Keychain gives the same PRF output on every Apple device, so its slot just works. For a separate passkey, the two devices compare a short code, and the code is made so the server can't cheat: the new device first sends only a hash of its public key and a random value; the signed-in device answers with its own random value; the new device then reveals; both show six digits worked out from all of that plus the budget's current signing public key, key version and log position. The server relays the messages but had to commit before it saw the other side's value, so it can't search for a key that gives the same digits. **The person confirms the digits on both devices.** The signed-in device then seals the budget key to the new one, which opens it only after its own confirmation and adds its own slot in a signed entry. Three attempts, 10 minutes each. A cancelled attempt adds nothing and changes nothing.
- **AES-GCM limits.** Random 96-bit nonces, and far fewer than 2^32 seals per derived key; a key version change resets the count. AES-GCM doesn't commit to its key, which is harmless here because every key is 256 random bits and never chosen by another party.
- **Quantum computers.** The log and snapshots are sealed with symmetric keys. The key slots and the bank inbox use X25519, which a large quantum computer could break. Hiding the slots' public halves from the server (above) means a copy of the server's data alone doesn't give such an attacker a slot to attack; the inbox public key can't be hidden, so stored bank runs would be exposed, and no claim is made about either (1.2). A post-quantum hybrid is later work.

### 5.3 What the server stores: a sealed, signed log

`BudgetStore` keeps, per budget, a log, snapshots, the bank inbox and the bank links (5.5), and no budget tables.

**Entries.** One entry is the set of row changes that one edit, one or more bank runs, or one day's scan made. It holds **results** (rows), not operations: a device applying an entry writes rows and re-runs nothing. Each entry carries:

- in clear and signed: its number, a random entry id, its time, its kind (edit, bank, scan, key or slot change, sign-out, data migration, key-change intent, cancel), the writer's device id and that device's own counter, the key version, the schema version, the **processing version** (below), the last bank run it has filed with the receipt for the runs it files (5.5), the date its scans have reached, and the signature;
- sealed: the row changes; for an edit, the time the person made it; and the last entry number and hash this device has seen from every other device;
- associated data: the budget id, the number, and the hash of the entry before it. Hashes cover the sealed bytes, the nonce and the clear fields.

Bodies are padded to size steps (256 bytes, 1 KB, 4 KB, 16 KB, 64 KB). A change set larger than 64 KB is split into parts that the server appends in one step or not at all.

**What the row changes cover.** Every table an edit or a bank run writes, not only today's `SYNC_TABLES`: also `audit_log`, `txn_key_move`, the bank log (`bank_event`, `bank_page`) and its counter. Section 6.2 lists every table.

**What the server checks on every append**, without reading anything sealed. The rules of the log itself are one piece of code that the server and every device both run (`docs/privacy-keys.md` 7.1), so an entry a device would refuse is a refused write and never a stored entry that stops every device:

1. The signature, against the current signing key, and the key version.
2. **Compare-and-swap:** the device sends `{ base: N, entries }`, and the server appends all of them or none, and only if the log's last number is `N`; otherwise it answers with the entries after `N`.
3. **Safe to resend:** if it already holds an entry with the same entry id, it answers "already stored" and stores nothing. Without this, a write whose answer was lost would be redone on top of itself, and `budget/assign`, which adds, would assign twice. This takes over the job of `edit_seen` (`routes/sync.ts`).
4. **Time:** an entry's clear time is for ordering only. The writer uses the later of its clock and one millisecond after the entry before, so one device with a fast clock can't block the others. The server refuses a time more than 5 minutes from its own clock, either way, which catches a broken client and nothing more (4.4).
5. **Bank runs first:** a write that holds an edit is refused while a complete bank run is waiting, unless the same write files that run first. A client too old to file (below) keeps its edits on the device until it updates. Key and slot changes, key-change intents and their cancels, and sign-out entries are **never** held back by this check or by the breaker: a lost phone can always be signed out and a passkey removed, even while a bank update can't be read.
6. **Filing:** the runs named must be the next ones, and the receipt must match all of them (5.5). The scan date may only move forward.
7. **Limits:** the breaker refuses edit, bank, scan and data-migration appends at 90% of a daily limit, as writes are refused today. The kinds it never holds back have a small daily count of their own for each budget, so they are not a way around it.

The server can't check what it can't read: that scans and bank runs were filed in the right order among themselves (5.4) is the device's job, covered by tests with two engines and by the processing version.

**Redoing a refused write.** Today the engine can't undo an edit: one edit is several SQLite batches plus `derive()`, and the copy drops the change-log triggers (`local/engine.ts`). The copy therefore becomes two things: a **confirmed base** (the state at the last entry the server accepted) and a **queue** of edits not yet accepted, each kept as the request that made it, with the time it was made, as the offline queue is today. The screens show base plus queue. To send, the engine runs the queued edit on the base with triggers that record each changed row, and builds the entry from that record. When the server refuses, the engine drops the result, applies the newer entries to the base, files any waiting bank run, and runs the queue again. Two things make a re-run give the same result. **Ids are an input, like the clock:** today a route makes a new row's id from the clock and randomness (`routes/transactions.ts`), so a re-run would give the row a new id and later queued edits of it would fail; ids are instead derived from the queued edit's own id. **The time the person made the edit travels with it**, sealed, so "the most recent edit wins" between two devices works as today (`editTime` in `routes/sync.ts`) and an edit made on the last day of a month acts on that month. A queued edit can still fail the route's own checks on the newer base (the category was removed meanwhile); the person is told, as a refused offline edit is today. The redo is tried a few times, then waits; it can't spin.

**Processing version.** Applying an entry needs no logic, but filing a bank run runs the matching code, and a tab left open keeps old code (`sw.js` serves the saved shell). The log holds the lowest app version allowed to file bank runs or run scans, as `DERIVE_VERSION` does for derived numbers. An older client shows "Update Ledgerline to continue" for anything it would write. A client that meets an entry with a newer **schema** version than its own can't apply it at all, so it stops there, for reading too, with the same message.

**Migrations.** Today the copy runs the server's budget migrations itself (`local/engine.ts`). After the move there are two separate lists: **store migrations** for the server's own tables (log, inbox, bank links), which a device never runs, and **budget migrations** for the copy, which only devices run. A migration that rewrites data (today's one-time jobs such as `refile_payees`, or a migration like 0008) is never plain SQL on each device: the first device on the new schema version writes it as one log entry, and the others apply it as rows.

**Snapshots.** A device writes the whole base, bank log included, sealed, in chunks, with a sealed and signed manifest: snapshot id, chunk count, each chunk's hash, the entry number and hash it stands at, a hash of every table, and hashes of the chain at regular checkpoints. Two checks stand between a snapshot and the deletion of anything older. First, the writer downloads it again and opens it, which proves it was stored whole. Second, a snapshot counts as **checked** only when a device has rebuilt the budget independently, from the snapshot before it plus the entries since, and got the same table hashes; this runs rarely, and for a person with one device it is that device, in a fresh database. Other devices compare their own table hashes when they pass the same entry, so two devices that have drifted apart find out. The server keeps the snapshot before the newest checked one, and every entry and filed bank run since that older snapshot; this one rule is the only one by which entries and runs are deleted. A device remembers the last checkpoint hash it saw as well as its position.

**A lying server: what is and isn't caught.**

- It can't forge or alter an entry or a snapshot.
- **Rollback.** Each device keeps the last number and hash it saw in a place separate from the copy, and nothing the server says clears it: not a new sync epoch, not a refused edit, not a revoke. A download that doesn't reach that position shows "The server's copy is older than this device's" and stops.
- **Holding back** new entries from one device can't be told apart from "nothing new" by that device alone.
- **A fork** (two devices each shown a different branch) can't be seen by one device alone. Because each entry carries what its writer last saw from the others, a fork shows the moment any entry crosses between branches. Settings → Sign-in also shows a short code for the log's position that can be compared across two devices by eye.
- A **new device** can be shown an older, consistent past. Setting one up shows "Last change: {date}, from {device}" to confirm.

So the claim is "a device notices if the server rolls back what it has seen", not "the server can't hide changes".

**No restore (owner, D-85).** Today a restore is the operator rolling a store back (`docs/runbooks/restore.md`, D-77). A sealed budget can't be checked or repaired by the operator, and the owner doesn't want a restore in the app. So there is none: the runbook and the undo (D-77) are retired at the cutover, and Cloudflare's point-in-time recovery is no longer used for budgets. The one exception is the way back during the move itself (section 8).

**A stopped device keeps its data.** When a device stops because the server is behind it, or because the server's side is damaged, the copy stays open to read and the full backup (5.8) still works. Today the app wipes a copy when the server answers that it was turned off (`checkSignedOut` in `apps/web/src/copy/copy.ts`), on a plain flag anyone who can write to the database could set. After this design the copy on a device may be the only good copy, so a copy is **wiped only on a signed sign-out entry in the log**; a plain flag from the server locks the copy until the next sign-in and never deletes it.

**There is no way forward either.** If the server truly lost a budget's newest entries (a platform fault, a bug), every device that had seen them stays stopped: readable, exportable, but unable to send. A repair in which the most advanced device publishes its copy as the new truth is possible to build, and is not built, because the owner chose no restore (14.3).

**The remembered position** is kept apart from the copy but in the same browser storage. "Clear website data" removes both, and a Safari tab that keeps no copy has none; such a device counts as new.

### 5.4 All budget work moves to the device

What the engine runs today: every screen, and six kinds of edit while offline (`OFFLINE_EDITS` in `apps/web/src/copy/copy.ts`). Every other edit and all background work run only on the server. The job runner is written against Durable Object storage (`store/jobs.ts`), the engine's environment has no Plaid keys and a sync starter that does nothing (`local/engine.ts`), and some handlers mix Plaid calls, token handling and budget writes in one function (`routes/settings/connections.ts`, `finalizeConnection` in `sync/process.ts`). So:

| Work                                                   | Today                                         | After                                                                                                                                                                      |
| ------------------------------------------------------ | --------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Every edit (`routes/*.ts`)                             | Checked and stored by the server              | Run in the engine; the result is a log entry. Each route is first proved to give the same rows in the engine as on the server (a mutation twin of `engine-routes.test.ts`) |
| Bank sync: fetch, and reading balances                 | `BudgetStore` alarm jobs                      | Stays on the server; each run is sealed (5.5)                                                                                                                              |
| Bank sync: apply, process, heal, finalize              | `BudgetStore` alarm jobs, 25 events a step    | The engine, when the app is open, from the sealed inbox                                                                                                                    |
| Daily scan                                             | An alarm at 5:00 in the budget's time zone    | The engine, when the app is open: once for each day missed, in order, in the time zone the budget had that day                                                             |
| Maintenance                                            | An alarm at 2:20                              | The engine, once per open day (its work is safe to do late and needs no replay per day)                                                                                    |
| Handlers that mix Plaid calls and budget writes        | One function                                  | Split: a Plaid call on the Worker, a budget write in the engine (linking and Setup are the big ones, 5.5)                                                                  |
| The bank log (`bank_event`, `bank_page`)               | Server only, append-only by trigger           | On the device, with the same triggers, stored beside the main copy and appended in chunks, so each save doesn't re-encrypt it all                                          |
| Raw Plaid pages (`raw_page`)                           | Server only, kept for ever                    | Not kept (owner, D-85). A sealed run is deleted once a checked snapshot covers it                                                                                          |
| Health and alerts about a budget                       | Server writes them                            | The engine writes them                                                                                                                                                     |
| Bank link state on screens ("needs repair", last sync) | Read from `connection`, written by the server | A small table on the device, outside the log, filled from the server with each inbox check                                                                                 |

Edits that lean on the server today and need a replacement, found by the review: account close reads `change_log` to see what changed (`routes/account-close.ts`), which the copy doesn't keep; the write breaker and the usage cap; the setup step, which depends on whether this user may link banks; and Plaid's webhook handler, which sits inside the budget's routes. Each is listed in 6.1.

**How bank runs are filed. This is where four things must change (decided by the owner, D-86).**

Today's server can't simply be copied onto the device, for reasons the reviews found in the code:

1. **Times.** Several times that decide what is shown and counted are today the clock of whichever server step ran: a row's arrival and removal are the apply step's clock (`bank_txn.created_at`, which D-67 reads); "pending row vanished" is the processing step's, or the 2:20 maintenance's; D-68's `drift_since` and the balance time are the finalize step's. A device can't know when those steps "would have" run.
2. **Order, and transfers.** Today the server processes the next 25 events of any link, and the links' jobs take turns. Transfer matching looks only inside one batch (`sync/file-fresh.ts`): two sides of a transfer pair by themselves only if they happen to be filed together, which today depends on timing (the 4-hour backstop starts every link together, so it happens often). A device filing one run at a time would never have two banks' rows in one batch, so **a transfer between two banks would never pair by itself**.
3. **Edits in the middle of a run.** Today an edit can land between two steps of a run, and a run can sleep until midnight UTC at a daily limit with half its rows applied. On the device a run is filed whole.
4. **Idle accounts.** Every link is fetched every 4 hours, news or not. For an account nobody opens that is thousands of sealed runs waiting, and a locked-out person's bank data collected for nothing.

The rules:

- **A1. One time per run.** Everything a run causes is stamped with the run's time: the moment the server completed fetching it. Today's times are seconds to minutes later, and hours later only while the app rests at a daily limit or a step is retried.
- **A2. One run at a time, in arrival order, and transfers look back.** The server numbers a budget's runs 1, 2, 3 as they complete, and a device files run 7 fully (apply, process, heal, finalize, in steps of 25 events as now) before run 8. So that transfers between two banks still pair, transfer matching also looks at rows already filed in the last days that have no partner yet, not only at the rows of the batch.
- **A3. No fetching for an account not opened for 90 days.** It starts again when the person next opens the app; rows that came meanwhile are stamped then.
- **A4. An edit never lands inside a run.** The run is filed whole, then the edit.

**One order for everything.** On open, a device works through the time since its last entry strictly by time: each bank run at its run time, and each missed day's scan at 5:00 that day in the time zone the budget had then, merged into one sequence; only then its own queued edits. Two devices given the same inbox therefore produce the same rows.

**The server changes first, the device second.** Phase 3 makes today's server follow A1, A2 and A4, on plain data, where every effect can be seen and measured on the owner's budget. That is real work on the sync code, not a setting: a run gets a number, a time and a "fetched" state (a migration on `sync_run`); once a run is fetched it is resumed, never fetched again; one run is processed at a time for the whole budget; maintenance stops catching up processing; and an edit that arrives during a run waits for it. Today a failed run is fetched again from the unmoved cursor and an abandoned one has its pages deleted (`sync/steps.ts`), and those paths change, so the guarantees in `docs/sync-spec.md` ("the cursor never moves backwards", "retries add nothing") are restated for runs and tested again. Only then is the same code moved to the device, and phase 4's shadow run can compare the device with the server exactly: the same runs, the same times, the same steps, compared without row ids.

**One write can file several runs.** After days away many runs are waiting. The device files them on a working copy of the base, in the one order above, and sends them in one compare-and-swap write with a receipt for all of them. If another device got there first, the write is refused and thrown away; on the redo the base already shows those runs filed. No lease is needed between devices, and a phone put in the background mid-run loses nothing. Tests with two engines cover bank runs, scans and their order.

**Memory.** The design asks the engine to hold more than one database at a time (the base, the working copy for filing, and now and then a rebuilt copy for the snapshot check), each with the bank log. Today there is one, exported whole on each save. Phase 0 measures peak memory on the owner's iPhone with all of them open, and decides from that whether the queue's view is a second copy or an overlay on the base.

**Step sizes stay as they are**: 25 events, until the owner accepts a change. Small steps also keep the app answering, because the engine handles one message at a time (`local/web-entry.ts`).

**Routes take their clock as an input.** Today the engine uses the device's time plus a saved offset. Filing a run uses the run's time; a scan uses 5:00 on its day; an edit uses the entry's time, which the server bounds (5.3).

### 5.5 Bank data: fetched in the background, sealed at once

- **Bank links stay on the server.** A server-only `bank_link` table holds, per link: the access token (under `TOKEN_KEYS`, with the same connection id and key version it was encrypted with), the Item id, the cursor, the fetch lock, the link time, and the fetch state (ok or needs repair, the last error, the last fetch, a re-sync request). A Worker-secret HMAC covers the budget id, link id, Item id, token and cursor, so a row can't be invented or copied into another budget; the lock changes every step and is not covered. Rows copied from `connection` by a migration have no HMAC (a migration is plain SQL and holds no secret); a one-time job stamps them, and the fetch step refuses unstamped rows after the cutover. The HMAC can't stop an **earlier** stamped row from being put back; the run manifest catches that (below). Everything that counts or reads a budget's banks on the server today reads `connection` (the 30-day rest of idle budgets, the wipe check, delete account, webhook routes and their registration, the backstop, the lifetime link count, the duplicate-Item check: `store/budget-store.ts`, `store/account-life.ts`, `routes/people.ts`, `store/budget-jobs.ts`, `store/directory.ts`, `store/router.ts`, `routes/ops.ts`, `routes/settings/connections.ts`); all of it moves to `bank_link`, with tests, or a sealed budget would look like it had no banks and could be wiped with live Items.
- **The fetch step stays on the server**, on alarms and webhooks as today, but it does more, in more steps. Today it never parses a page and stores no checksum, because even hashing 200 KB costs over a millisecond (`sync/steps.ts`). After: fetch a page; in a step of its own, check its shape, count its rows, seal it and hash it; at the end of a run, one step each for Plaid's balances and liabilities, which today's finalize step asks for (if those calls fail the run is stored without them and says so); then a last step that signs the manifest and records the fetch as done in `bank_link`. Each step is measured against the 10 ms rule in phase 0, and the page size is lowered if a step doesn't fit. "Last synced" on screens then means fetched; rows show once a device has filed them.
- **A run is whole or absent.** Its pages are staged, as `sync_page` does today, and a device sees a run only when it is complete. If Plaid reports that data changed mid-run, the staged pages are dropped and the run starts again from its first cursor, as today. The cursor moves in the same transaction that completes the run, and the run's first cursor is kept with it.
- **Each run is sealed and signed.** The pages and balances are sealed (HPKE) to the budget's inbox public key. The Worker then signs a **run manifest** with a key held as a Worker secret: budget, link, the inbox key it sealed to, run number, how often it restarted, the hash of each sealed page in order, the run's time and the time of the run before, hashes of the link's cursor before and after the run, and the hash of the manifest before it. The app has the Worker's public key built in, with a key id and room for an old and a new key at once, so the key can change without stranding open tabs. The key is derived from an existing Worker secret, so the owner pastes nothing. A device files only the next run number, checks the chain, refuses a run sealed to any inbox key but the current one, and refuses a run whose "cursor before" isn't the "cursor after" of the last run it filed for that link. So someone who can write to the database but has no Worker secret can't invent a run, replay one, drop one from the middle or the end, mix pages of two attempts, or rewind a link without the next run showing it.
- **Receipts.** Inside each sealed run the Worker puts a random value and keeps only its hash. A filing write must show a hash over the values of **every** run it files (5.3), which proves the device opened all of them. Filed runs are deleted only by the snapshot rule in 5.3, and each run's first cursor is kept after the run itself is gone.
- **A run that can't be filed.** If a device can't open or process a run (a bug, a damaged page), nothing is skipped: edits wait on the device (5.3), the app says "Ledgerline can't read your bank's latest update yet", and a fixed release files it. The server can fetch a run again from its first cursor, which gives the same changes (to confirm in phase 0 that Plaid lets an old cursor be used again). Fetching a link's whole history again from nothing is **not** offered: Plaid then sends only what exists now, so removed rows and pending rows that came and went would be missed, and that would change how money is counted.
- **Linking and Setup.** Today the exchange also writes accounts, card categories and starting balances on the server (`routes/settings/connections.ts`), and sync waits until Setup is done. After: the app asks the server for a link token in a session with a recent passkey check, signed with the budget's signing key; the server remembers which budget the token is for (`plaid_link_slot` exists for this and is unused today) and the app opens Plaid's page (5.7). **The server doesn't wait for the person to come back:** Plaid's public token is good for only about 30 minutes, and an Item with no access token would be a lifetime link used for nothing. So the Worker exchanges on Plaid's "link finished" webhook, and an alarm also asks Plaid about every open link token. It stores the token in `bank_link` and seals what Plaid says about the link (its bank, its accounts, their balances, the link time) as that link's first run. The device writes the accounts, categories and starting balances from it, and the first transactions run comes after. The count of links ever made moves to the Directory.
- **Repair and removing a bank.** Repair (Plaid's update mode) exists today. Removing a bank at Plaid does **not**: there is no `/item/remove` call in the code, and deleting an account with banks is refused. It is new work, and what becomes of the bank's accounts in the budget is decided: they stay, marked "not linked" (D-87). Asking for a link token (to add or to repair a bank), removing a bank and deleting an account each need a recent passkey check **and** a request signed with the budget's signing key, so a stolen session cookie alone can't remove a bank. The Worker removes Items by itself only when an account is deleted or expires (5.8), and that code path refuses an admin's budget and refuses to run on Plaid Trial, so the owner's 7 Items can't be removed by a job.
- **Webhooks.** Plaid's webhook still reaches the Worker and is verified. It starts a fetch, finishes a link (above), or marks the link "needs repair" in `bank_link`. The handler moves out of the budget's routes.
- **Limits.** Fetching pauses at 70% of a daily limit, as sync does today. An account not opened for 90 days is not fetched (A3).

What this protects: someone who reads or writes the database learns no bank data. What it doesn't: someone with the database and the Worker's secrets can ask Plaid for each link's data, as today. Replacing the bank keys so that older stolen copies stop working is tabled by the owner (D-85).

### 5.6 Identity and metadata

- **No email.** Already true for sign-ups: `user.email` gets a random value (`routes/signup.ts`). The owner's row keeps its value, because the saved copy on the owner's devices is filed under it (`vault.ts` `recordKey`). Plaid's own page may ask a person for a phone number; that is between them and Plaid, and the policy says so.
- **No name (owner, Nov 10, D-85).** Sign-up requires a name today (`routes/signup.ts`). The field goes: sign-up asks for a passkey and nothing else. Settings → Users shows each account by its date.
- **Budget name and bank names** move into the sealed budget; the Directory's `budget.name` becomes a fixed word. The server check that compares a typed budget name on delete account (`routes/people.ts`) moves to the device. That check is against a slip, not a lock: what stops a stranger is the request's signature with the budget's key and the recent passkey check (`docs/privacy-keys.md` 11). A hash of the name sent for the server to compare would add nothing a signature doesn't (any holder of the key can make it) and would give the server a guessable name's hash, so the typed name is checked on the device only.
- **Passkey names, device names, user agents:** kept only as long as the passkey, device or session; names are the person's own words and can be blank.
- **Usage events and notes** (`usage_event`, `usage_note`, `usage_daily`) stay on the device, sealed with the budget. A person can export their own. The operator gets none from other people.
- **Logs.** Paths become generic (`/api/log`, `/api/inbox`), so a path no longer holds a transaction id. Phase 0 checks what Cloudflare's invocation logs record per request; if that includes an IP address, they are turned off before any claim about IP addresses is made.
- **Turnstile** (open sign-up, `docs/open-signup.md` 13) needs a script and a frame from `challenges.cloudflare.com`. A separate page on the app's own address isn't enough: a script there could still reach the address's stored data, including the keys held for a page refresh. So the robot check lives on a **second address** (a second free Worker on its own `workers.dev` name) that holds nothing, and hands back a one-use token; the app itself never loads an outside script.

### 5.7 No outside script where the keys are

**Done (Nov 11, 2026): hosted Link is the only way, and the CSP allows no outside host.** Before, the CSP allowed `https://cdn.plaid.com` as a script source, and Plaid Link's script ran in the same page as the copy. With the budget key in the page, that is no longer acceptable.

Use Plaid's hosted Link: the app opens a page on Plaid's own site, the person links the bank there, and comes back. The app's CSP becomes `script-src 'self' 'wasm-unsafe-eval'; connect-src 'self'` with no `frame-src`. The app finishes a link by asking the server (5.5), not by trusting where the browser lands. The Worker asks Plaid for the same products as today and no more.

To check in phase 0, **in Plaid's Sandbox or in repair mode on an existing link only, because a test link on Plaid Trial uses up one of the 3 lifetime links left**: that hosted Link is offered to us; and what happens on an iPhone when a bank's own sign-in returns to Safari while the person started in the Home Screen app, which has separate storage. If hosted Link can't be used, the fallback is Link on the second address described in 5.6, never on the app's own.

Also: drop `'unsafe-inline'` from `style-src`, add Trusted Types where the browser has them, and keep the CSP test that fails when any source loosens.

### 5.8 Recovery, backup, deleting

- **Recovery key.** 256 random bits, shown once at sign-up as words or letter groups. HKDF splits it in two: one half proves to the server that the person may add a passkey (by a signature, so the server stores only a public key and nothing reusable passes through it; `docs/privacy-keys.md` 4.2); the other half gives the recovery slot's key pair (5.2). It replaces the recovery code. Making a new one changes the key version.
- **No reset, by anyone.** The owner's runbook recovery (`docs/runbooks/setup.md`) and the owner's device link (D-27) can give back a sign-in but not a budget: a passkey added that way has no slot until a device that holds the key adds one. So the owner gets a recovery key too. This changes "not for admins" (`docs/open-signup.md` 4; owner's yes, D-85).
- **Full backup.** Made on the device, after a fresh passkey prompt, which stands in for today's 15-minute rule on the server export. Sealed with the recovery key by default, so no password and no password-stretching code are needed; or plain, with a warning. `GET /api/export/dump` goes away. It takes data out; nothing loads it back. The two open items about restoring a backup (`docs/build-plan.md`) close as "not wanted".
- **Deleting an account.** The order in `docs/open-signup.md` 12 holds: sessions, devices and routes go first; then the server removes each Item at Plaid from its stored token, with retries; then the store wipes itself and the Directory deletes the user. What protects the remains is that the server never had the key. Whether Cloudflare's recovery keeps a wiped store's bytes is stated two ways in the docs; phase 0 tests it, and the claim says "up to 30 days" until then.
- **Idle accounts are deleted (owner, D-85), carefully.** The time used is the later of the account's creation and the last request by any member of the budget (`user.last_seen_at`, written at most hourly on a signed-in request, and empty for a user never seen). The Directory's daily cron works in two stages: it **marks** an account idle at 24 months (under a key of its own; `idle:` already means the 30-day rest of a budget with no banks), and 30 days later moves it into the same `deleting` state that Delete account uses, so there is one deletion path; any sign-in in between clears the mark. It never touches an admin's account or one an admin has turned off, starts at most a few deletions per run, and health shows how many are marked, so a bug shows before it destroys anything. A delete that can't finish (Plaid is down) is tried again daily. With no email there is no way to warn someone who never opens the app, so sign-up and the policy say it plainly, and Settings → Privacy shows the date. This replaces "nothing is deleted for being idle" (`docs/open-signup.md` 1 and 9).
- **Telling people about an incident.** With no email, notices show in the app at sign-in. A notice can require action before the budget opens, such as "make a new recovery key". The policy says this is the only channel.

### 5.9 Public, comparable releases

- **The repository is already public** (checked Nov 10, 2026), so the code is open today and branch protection is available. Its docs held the owner's own purchases and bank names; they were taken out on Nov 10, 2026 (D-85). The git history keeps the old text.
- The web build is made reproducible: the same commit gives the same files, byte for byte.
- The deploy workflow publishes the list of file hashes for each release with a build attestation (free for public repositories), and Settings → About shows the release's commit and hash.
- **Built (Nov 12, 2026, D-96):** `tools/ci/reproducible-check.mjs` in `ci`, `/release.json`, the attestation step in `deploy.yml`, Settings → About, and the steps to check a release in `docs/runbooks/verify-build.md`.
- Anyone can then compare what the site serves with what the public build made. This covers the app's code. It says nothing about what the Worker runs, and it can't catch code sent to one person once (4.2). The policy says both.

### 5.10 Who can ship code

After this design, the code path is the attack surface. Today every Claude session merges its own PRs and each merge deploys (`CLAUDE.md`, D-51). The owner agreed (D-85) that:

- A change to the key and sealing code, the fetch-and-seal step, the CSP (`apps/web/public/_headers`), `sw.js`, the build, or `.github/` is merged by the owner, never by a session. `.github/CODEOWNERS` lists those paths, `node tools/ci/owner-paths.mjs` finds them in a branch, and `CLAUDE.md` makes it a condition of a session's own merge (built Nov 10, 2026; D-88). GitHub can't enforce it: every PR is opened under the owner's account, and an account can't approve its own PR, so a required review would block everything. **Replaced on Nov 12, 2026 (D-94):** the owner removed this rule; a session merges such a change like any other, and the paths are only named.
- No new runtime dependency in the key and sealing code without the owner's review.
- Hardware-key or passkey two-step sign-in on Cloudflare, GitHub and Plaid (`docs/threat-model.md` says so already), and a Cloudflare API token that can deploy the Worker and nothing else.

### 5.11 What stays the same

Passkey sign-in, sessions, CSRF checks, rate limits, the breaker and fair-use shares (they count requests, entries and bytes, not content), the one cron, deploys by merge, `TOKEN_KEYS`, the 7 bank links, the Money rules in `packages/domain`, and link repair. The 15-minute recent-passkey rule stays for linking, repair, removing a bank and passkey changes, and becomes a passkey prompt on the device for backups.

## 8. Moving the owner's budget

The owner's budget is real, migrations are forward-only, and 7 of 10 lifetime bank links are used. Each step that merges a migration needs the owner's yes (`CLAUDE.md`). **No bank is linked, re-linked or removed at any step, and no bank key changes.** The whole move, and the way back, is first rehearsed in tests with the owner's own full backup loaded locally (never committed).

1. **Before anything:** a full backup. PRF checked with the owner's existing passkey on every device (an open item in `docs/build-plan.md`).
2. **Store and budget migrations are split** (5.3), so a table like `bank_link` never reaches a phone. From the cutover until step 8 starts, no budget migration ships.
3. **A release that knows "sealed" and "frozen"**: old code paths (routes, alarms, webhooks) refuse to touch a budget marked sealed, and refuse every write and job on one marked frozen. It ships well before the move, so that a later automatic code rollback (`deploy.yml` rolls back on a failed smoke test, and a rollback undoes code, not data) lands on code that obeys the marks.
4. **`bank_link` gets a copy of each token**, with its connection id, key version and Item id, by a migration; a one-time job stamps the HMACs. The cursor and the lock stay in `connection` until the cutover. Each of the 7 links must show that the copied token decrypts and Plaid accepts it (a fetch, or Plaid's "needs repair" answer for a link that is waiting for one).
5. **A1, A2 and A4 on the server** (phase 3), then the **shadow run** (phase 4), matching on the owner's budget for two weeks.
6. **Cutover.** The device proves, with a fresh passkey prompt and with the typed recovery key, that both slots open the new budget key. Then the server **freezes** the budget: no writes, no jobs, with a time limit after which it unfreezes untouched. Frozen, it checks: no run staged or in progress; processing caught up with everything applied; no maintenance catch-up or one-time job part-way; no re-sync asked for; and the device's copy matches the server's dump hashes, table by table, including the columns `/api/sync` leaves out today, the bank log, and the tables with no sync trigger (usage, notes). In one transaction it then stores the device's first signed snapshot, slots and inbox public key, copies each link's cursor into `bank_link` and saves it as the link's **cutover cursor**, sets the inbox to start after the last run the server itself applied, deletes the old processing jobs, and marks the budget sealed. This is the one time a device makes a key for a budget that already exists.
7. **A week of normal use**, with the old tables untouched and the old code still deployed. During that week the server refuses to link or remove a bank for this budget, so `connection` and `bank_link` can't drift apart. And during that week only, there is a way back that does not depend on the new keys working, because the cases that need it are the ones where they don't: a route that takes the owner's signed-in session with a fresh passkey prompt (sign-in doesn't need the budget key). It clears the mark, sets each link's cursor back to its cutover cursor, and the old code runs on the old tables. Each device leaves the sealed budget only after the person confirms it there with a passkey prompt. The cost: edits since the cutover are lost unless they are typed again (the app lists them first); bank rows since then come again from Plaid with new arrival times, so a starting balance still settling (D-67) or a bank difference (D-68) could count differently; and it depends on Plaid accepting the older cursor (phase 0). It is a one-time safety net for the move, not a feature, and its route is removed with step 8.
8. **Emptying the old tables.** Every old budget table is emptied, not only the bank ones: transactions, payees, `audit_log`, `change_log`, usage, connection names and tokens. `bank_event`, `bank_page` and `raw_page` refuse deletes by trigger, and deletes on synced tables write `change_log` rows; done at once, seven banks' rows could pass the free plan's daily row limit and rest the app. So: a store migration drops those triggers on the server only (the device keeps its own), and a stepped job under the breaker empties the tables over days. Measure the row count first. From here there is no way back. _As built (D-99, then D-106): the job ran from the owner's tap, and on Nov 13, 2026 the owner had a store migration (0010) drop every old table at once instead; the job and its check are gone._
9. **30 days after step 8 ends**, point-in-time recovery no longer reaches plain text. Before "we keep no readable copy" is said (1.1), check that nothing readable is left: the tables are empty, the Directory holds no budget name, and the question whether SQLite keeps deleted rows in freed pages inside a Durable Object is answered (phase 0). _As built (D-106): no check runs. The 30 days count from the day store migration 0010 ran; the phase 0 question is still open._

## 9. The free plan

- Server CPU: storing a sealed row, checking a signature and an HMAC are small. The fetch step adds a shape check, a seal and a signature over a page of up to about 200 KB; measure it against the 10 ms rule (`docs/measurements.md`), and lower the page size if needed.
- Durable Object rows fall: one row per edit, and a few per bank run, not one per changed row plus `change_log`.
- The 4-hour backstop makes about 42 runs a day for 7 links, most with no new rows. One write can file many runs (5.4), and fetching stops after 90 days idle (A3), so a return after 3 weeks is a handful of writes, not hundreds. Measure the size of a waiting inbox and the time to file it in phase 0.
- Device work rises: filing bank runs, sealing, snapshots and their check. Measure on the owner's iPhone in phase 0: opening a sealed snapshot of today's budget; filing a 100-row run; replaying a month away; the size of the bank log; a save with the bank log kept beside the copy.
- Nothing in the design costs money to build or run.

## 11. Outside the code

None of this is needed to build the design, and none is paid for today (the $0 rule stands, D-85).

- **A privacy policy and terms** written from sections 2 and 4: what is stored, what is sealed, who else handles data (Cloudflare, Plaid), how long, how to delete, the "no reset", 90-day and 24-month rules, what a locked-out person can do at Plaid, and that in-app notices are the only way we can reach a person. - **A security contact**: a `security.txt` and a short disclosure policy.
- **Only if sign-up is ever opened:** legal advice on the rules for companies that hold other people's financial data; Plaid Production, which has its own review and a price per linked Item; and, to turn "our word" into more than that, an outside audit.

## 12. What this design doesn't do

- It doesn't hide bank data from Plaid, from Cloudflare as the platform, or from the Worker's memory between Plaid's answer and the seal.
- It doesn't take the key to a bank link away from the server.
- It doesn't stop changed code, in the app or the Worker, from reading a budget or bank data (4.2).
- It doesn't stop the server from lying about bank data or, within bounds, the time (4.4), or from holding back changes (5.3).
- It doesn't hide IP addresses, times of use, counts, sizes or which banks from Cloudflare and the operator (4.3).
- It doesn't protect stored key slots and bank runs from a future quantum computer (5.2).
- It doesn't let two people share one budget. That needs each person's public key and a way to check it, which is its own design.
- It doesn't protect a budget on an unlocked or compromised device.
- It doesn't let anyone recover a budget whose keys are lost, and it has no restore.

### 14.4 Decided last (Nov 10, 2026)

- **A removed bank's accounts stay (D-87).** Removing a bank ends the link at Plaid; no new rows come. The accounts and every past row stay exactly as they are, the accounts are marked "not linked", and they keep counting in the budget and in net worth at their last balance. An account is hidden only by Close account, which runs at $0 (D-73).
- **The recovery key stays (D-85).** Sign-in is passkeys only. The recovery key is never used to sign in day to day; it exists for the one case when every passkey is lost, to add a new passkey and open the budget.

### 14.3 Considered and not chosen

- **The device keeps the bank key and the server only relays each Plaid call.** Stronger: nothing stored on the server could ask Plaid for anything. Not chosen because rows would arrive only while the app is open; the server couldn't remove an abandoned account's banks; and the owner's 7 bank keys would have to move to a device with 3 lifetime links left. A later switch is a medium job: the device's bank code is the same if it reads runs through one small interface, so it is built that way, but the three problems would each need an answer.
- **Other bank sources** (checked Nov 10, 2026 from public pages; nothing was tried). No bank link, or a bank file read on the device, are the most private and free, and both need Money-rules answers first (D-81 removed CSV import over two of them). SimpleFIN Bridge has each person pay about $15 a year for their own read-only link, with no lifetime limit, but sends less than Plaid (no merchant ids), so payee names and matching (D-63, D-65) would need rework. Akoya needs a business contract. Teller holds the connection as Plaid does. Direct access under the US "1033" rule is blocked in court and being rewritten.
- **Fetching a link's whole history again** as a repair. It would change how money is counted (5.5).
- **Symmetric key slots.** They are safe from quantum computers but make a key change lock out every other passkey (5.2).
- **A repair after the server loses data**, in which the most advanced device publishes its copy as the new truth. It is a restore by another name, and the owner chose none. Without it a budget whose newest entries the server lost stays readable on its devices and can't be sent back. It can be added later without changing the stored formats.

## 15. Review

### 15.1 v1 (Nov 10, 2026)

Two independent reviewers were told to break v1: one on the key design and the claims, one on the fit with the code. They made 39 findings, 11 of them critical; v2 fixed them. The critical ones:

1. "We can't read it, nor anyone who breaks in" was false: changed code can.
2. "We hold no access to your bank" was false for any shape in which the Worker sees the bank key.
3. Arrival time decides money (D-67, D-68); fetching only while the app is open would change it.
4. A new link's key was to be sealed and also removed after 24 hours; both couldn't hold, and removal burns a lifetime link.
5. `TOKEN_KEYS` also signs sign-in challenges; deleting it would break every sign-in.
6. Two devices processing the same pages would write the same rows twice.
7. A write whose answer is lost would be redone on itself; `assign` adds twice.
8. The phases sealed the budget before anyone but the server could sync banks.
9. The server can hold back entries or fork the log, and one device can't see it.
10. The server could make a device forget its position and then roll it back.
11. "Proof a stranger can check" was claimed for what the Worker does; nobody can inspect a Worker.

### 15.4 Still unverified, to settle in phase 0

**Settled on Nov 10, 2026** with Settings → Device check, on the owner's iPhone in Safari and in the Home Screen app, and on a desktop browser: Ed25519 and X25519 keys from seeds, HPKE, a signed and sealed entry, and an 8 MB snapshot sealed and opened in under 20 ms; the owner's existing passkey gives two different PRF secrets in one prompt.

**Settled on Nov 10, 2026, in Plaid's Sandbox** (no bank link used): `/link/token/create` with `hosted_link` gives our team a hosted Link page on `secure.plaid.com`, for the same products as today. The owner linked a made-up bank there on a desktop browser, and Plaid sent the browser back to the app's address given as `completion_redirect_uri`. The server then got the result with `/link/token/get` (the session's `item_add_results`, each with a public token), exchanged it, and removed the test Item. Not tested: the "session finished" webhook, which the app does not need.

**Settled on Nov 11, 2026: what Cloudflare's invocation logs hold** (field names read through the Workers observability API; no values were copied). For each request, the invocation log (`invocation_logs` is on) holds: the IP address (`cf-connecting-ip`, `x-real-ip`); a location for it down to city, postal code, latitude and longitude; the network's name and number; the user agent and language; the full address of the request, with any id in its path; the names of all request headers and the values of most (the cookie is replaced by `REDACTED`); TLS details; the response status; CPU and wall time. For work inside a store it holds the Durable Object's id and the names of the methods called. The app's own log lines made inside a store hold none of the request's fields; one made in a request was not seen in the 48 hours looked at, so that case is unchecked. Kept 3 days on the free plan. So, by 5.6: invocation logs are turned off before any claim about IP addresses is made, and until then Settings → Privacy says what they hold.

**Settled on Nov 11, 2026, in production:** the owner signed in again to a bank (update mode, which uses no bank link) from the Home Screen app on the iPhone. iOS showed Plaid's site over the app, the bank's own sign-in worked there, and at the end the person was back in the app on Bank connections.
