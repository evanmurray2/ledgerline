# Threat model

What each asset faces now, and what stops it (Nov 13, 2026). Every budget is locked (D-102): the server holds a signed, sealed log it can't read, and the budget is worked out on each device (`docs/architecture.md`). `docs/privacy.md` section 3 has the full list of who is defended against and section 4 the limits no design removes; `docs/claims.md` says which privacy claims are true now. A change to who can read what changes this page, `docs/claims.md` and `docs/privacy.md` in the same pull request.

## Assets and controls

| Asset                             | Threat                                                                                          | Control (where)                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| --------------------------------- | ----------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| The budget, as stored             | Someone who reads the store, a point-in-time recovery or a legal demand for stored data         | Only sealed entries, snapshots and bank runs, under the budget key that only devices hold (`packages/seal`, `docs/privacy-keys.md`); entries padded. The server has no budget tables and no code that reads them (D-106). What it can see is listed in `docs/privacy.md` 4.3: times, sizes, counts, link ids and states, passkeys and devices. Point-in-time recovery still holds the readable tables until 30 days after store migration 0010 ran (`docs/claims.md` claims 2 and 3).             |
| The budget, as stored             | Someone who can write to the store but holds no Worker secret                                   | Can't forge an entry, a snapshot or a bank run: each is signed by a device key or the Worker's stamp, and checked by the log's rules on the server and on every device (`packages/seal`, `seal/log-store.ts`). Rollback of what a device has seen is detected (the device keeps its last number and hash apart from the copy); a fork shows when an entry crosses between branches (`docs/privacy.md` 5.3). Holding back entries from one device is not detected.                                 |
| The budget, on a device           | A stolen or borrowed device; a revoked device                                                   | One AES-GCM blob in IndexedDB, its data key wrapped under HKDF(passkey PRF output ‖ a per-device share the Directory holds) (`apps/web/src/copy/vault.ts`); keys non-extractable, in memory only; locks after 10 idle minutes or 10 in the background (D-57); opens with no signal for 7 days. A copy is wiped only on a signed sign-out in the log, never on a plain server flag (`docs/privacy.md` 5.3). Accepted (D-45): someone with the unlocked device and its passcode reads the budget.   |
| The budget, on a device           | The server sends changed app code (a taken-over Cloudflare or GitHub account, a bad dependency) | Not prevented: bad code reads every budget opened while it is live, and the bank data fetched meanwhile (`docs/privacy.md` 4.2). Made visible afterwards: the web build is reproducible and attested, and Settings → About shows the commit and build hash to compare (D-96, `docs/runbooks/verify-build.md`). The release check covers the app's files, not the Worker. CSP allows only self and Plaid Link; `frame-ancestors 'none'`.                                                           |
| The budget, on a device           | Two devices work out different numbers (a bug, a bad migration)                                 | The twin tests prove an edit gives the same rows on every device (`apps/worker/test/twin.test.ts`). The device check sends an HMAC of what each device's screens show at one entry; a difference shows in Budget → Needs attention with Rebuild (D-116, `local/device-check.ts`). When an open runs budget migrations, the copy from before them is kept for 14 days and can be saved as a full backup (`copy.ts` `keepBeforeUpdate`).                                                            |
| The budget key and the ways in    | A stolen passkey or recovery key; a new way in added by someone else                            | The budget key opens only from a slot (a passkey's PRF secret or the recovery key's) in the log's public entries (`docs/privacy-keys.md`). New keys come in a signed write (D-114). Every key change made from a fresh way in (the recovery key, or a passkey added less than 7 days ago) waits 7 days as a planned change (D-89). Every device shows a notice for 14 days when a way in is added or removed, a change is planned, or the recovery key signs in (`apps/web/src/copy/notices.ts`). |
| The budget, lost                  | Every device lost; the Cloudflare account lost; damage found after 30 days                      | The log on the server rebuilds a lost device (`docs/runbooks/restore.md`). Losing every passkey: the recovery key opens the budget. Losing the account or finding damage late: only the full backup made on a device, sealed with the recovery key (D-99), kept by the person; Budget → Needs attention asks for one after 30 days without. No off-site backup, by the owner's choice (D-29). Losing every passkey and the recovery key loses the budget: nobody can open it.                     |
| Sessions                          | Theft or replay                                                                                 | Random 256-bit token in an HttpOnly, Secure, SameSite=Strict `__Host-` cookie; the Directory stores only its SHA-256; 24-hour absolute expiry (`src/http/auth.ts`); "Sign out other devices" deletes the rows. Linking a bank, a full backup and passkey changes need a passkey check within 15 minutes. A session alone opens no budget: the device still needs the budget key.                                                                                                                  |
| First sign-in                     | Someone else registering first                                                                  | The first passkey needs `SETUP_CODE` (a Worker secret, 32+ characters, constant-time compare), which stops working once an admin has a passkey (`docs/open-signup.md` 3.4). Added devices need a single-use 10-minute link from a signed-in device. WebAuthn challenges last 5 minutes in a signed cookie and are single-use; origin, RP id and user verification are checked.                                                                                                                    |
| Open sign-up (off, D-75)          | Scripted accounts, using up the free plan, a stranger as admin                                  | Off until `SIGNUPS` is `open`; the robot check runs on its own address (D-113, not deployed); the Worker checks the switch, CSRF and the robot check before any Durable Object request; per-IP rate limit, `MAX_USERS` and `SIGNUPS_PER_DAY`, checked again in the transaction that makes the account; a sign-up is never an admin; other users can't link banks on Plaid Trial and share half of each daily limit (`store/shares.ts`).                                                           |
| Plaid access tokens               | Leak from the store, logs or API                                                                | AES-256-GCM with a Worker-secret key and per-row key version, bound to the link (`packages/platform/src/token-crypto.ts`), and the link row under the Worker's stamp (`linkMac`); opened only in the fetch job and link repair; never returned by any endpoint; logs use an allowlist of fields. Someone with the store and the Worker's secrets can ask Plaid for each link's bank data (`docs/privacy.md` 3).                                                                                   |
| Bank data in transit              | A forged or replayed bank run; bank data pointed at another key                                 | Each page sealed to the budget's inbox key the moment Plaid answers, then the run signed by the Worker (`seal/runs.ts`); devices check the stamp and the inbox key's stamp before filing. On the device the bank log tables only grow, except a run the device filed itself and the log replaced (`migrateLocal`, `BANK_LOG_TABLES`).                                                                                                                                                             |
| Webhook endpoint (public)         | Forged webhooks triggering work                                                                 | ES256 `Plaid-Verification` JWT, key by `kid`, 5-minute `iat`, body SHA-256 (`packages/bank-provider/src/plaid.ts`); it only starts a fetch for a known Item.                                                                                                                                                                                                                                                                                                                                      |
| Ops endpoint                      | Token leak                                                                                      | `OPS_TOKEN` reaches only `GET /api/health` (link fetch times and usage, no budget data); constant-time compare; kept in GitHub environment secrets.                                                                                                                                                                                                                                                                                                                                               |
| Browser session                   | CSRF, clickjacking, script injection                                                            | JSON content type + `x-ledgerline` header + same-origin `Origin` on mutations (sign-in routes included); SameSite=Strict cookies; CSP allowing only self and Plaid Link; `frame-ancestors 'none'`; `Referrer-Policy: no-referrer`; HSTS.                                                                                                                                                                                                                                                          |
| Worker secrets and Plaid keys     | Exposure to unreviewed code                                                                     | GitHub `production` environment secrets, given to the Worker by `deploy.yml` (D-28), which runs only for a commit on `main` whose `ci` passed (D-30, D-49); not available to pull requests. There is no staging (D-36) and no manual deploy. The deploy token could already read them through a deployed Worker, so this adds no new path.                                                                                                                                                        |
| Plaid Items (10 for life, 3 left) | Burning slots by mistake                                                                        | Sandbox everywhere but production; update mode for repairs; Item meter and confirm step; the server refuses a new link at 10; only admins link banks (D-75).                                                                                                                                                                                                                                                                                                                                      |
| Request logs                      | IP address and location kept with each request                                                  | Cloudflare's invocation logs are off (D-112). The app's own log lines are kept 3 days and use an allowlist of fields.                                                                                                                                                                                                                                                                                                                                                                             |
| Availability                      | Daily free limits take the app offline; a fetch job that stops                                  | Account-wide usage from GraphQL Analytics; the breaker pauses background work at 70%, refuses writes at 90% and rests at 95% (D-40). Edits wait in the device's queue while the server rests. Budget → Needs attention names a bank link with no complete fetch for 24 hours (`screens/DeviceAttention.tsx`): there is no monitor (D-49).                                                                                                                                                         |
| Supply chain                      | Malicious dependency or action                                                                  | Lockfile, Dependabot, OSV-Scanner, dependency review, actions pinned to commit SHAs, zizmor and actionlint. Changes to the key code merge like any other once `ci` passes (D-94, which replaced D-88's owner review). A bad dependency in the app's files is the "changed app code" row above.                                                                                                                                                                                                    |

## Accepted

- Someone who can change the code the server sends reads every budget opened while it is live. The reproducible build shows it afterwards; it does not stop it. Hardware-key or passkey 2FA on Cloudflare, GitHub and Plaid is the main mitigation.
- Someone with the Worker's secrets can ask Plaid for each link's bank data, and point future bank data at a key of their own.
- A device that is unlocked, with its passcode, reads the budget and can sign in.
- Holding back entries from one device, and showing a new device an older consistent past, are not prevented (`docs/privacy.md` 5.3).
- Anything not in a full backup is lost with the Cloudflare account, or with every passkey and the recovery key.
