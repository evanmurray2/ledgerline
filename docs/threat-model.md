# Threat model

Every budget is locked (D-102): the server holds only a signed, sealed log, sealed snapshots and sealed bank runs that it can't read, and the device does all budget work. `docs/privacy.md` (sections 3 and 4: who we defend against, and the limits no design removes), `docs/privacy-keys.md` (the byte formats and what each side checks) and `docs/architecture.md` say how; `docs/claims.md` says which privacy claims are true now.

| Asset                     | Threat                                                                             | Control (where)                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| ------------------------- | ---------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Financial data            | Anyone reaching the Worker or its database                                         | The server has no budget tables (store migration 0010, D-106) and no budget key: what it stores is sealed on the device (`docs/privacy.md` 5.3). Passkey sign-in verified by the Worker (`apps/worker/src/routes/auth.ts`, D-27); every API request needs a server-side session in the Directory (`src/http/auth.ts`, `src/store/router.ts`), and the Worker opens only the signed-in user's own BudgetStore, chosen from the session's membership (D-37). A locked budget answers only `/api/log/*`, `seal/sealed-routes.ts` and the Plaid webhook (`store/marks.ts`). Only sign-in and the webhook are public. Cloudflare's 30-day point-in-time recovery still holds the store's readable tables from before the lock until 30 days after migration 0010 ran (Nov 13, 2026).                           |
| Budget key                | The server, the operator or a database writer reading or swapping it               | 256 random bits made on the budget's first device, never by the server, and never again for a budget that exists (`docs/privacy.md` 5.2). It is sealed (HPKE) to a public-key slot for each passkey (from its PRF output) and one for the recovery key; the slots' public halves are in the log, sealed under the budget key, and each carries a MAC from its own secret, which a device checks before it trusts what it unseals (`packages/seal`, `docs/privacy-keys.md` 4). Removing a passkey or making a new recovery key changes the key version. A key change made from a recovery-key sign-in or a passkey added in the last 7 days is held back 7 days, with a notice on the other devices (D-89, `store/way-in.ts`). Keys are non-extractable in memory; a page refresh holds derived keys only. |
| Sealed log and snapshots  | A server or database writer inventing, changing, replaying or rolling back entries | Every entry is signed with the budget's signing key and sealed under the budget key; its header binds the budget id, kind and number (`docs/privacy-keys.md` 6). The server refuses an entry not signed by the current key and checks the log's rules in the same transaction (`seal/log-store.ts`); a device walks the public chain from the genesis entry and refuses what doesn't follow. A server that drops newer entries stops the devices that saw them: there is no way forward or back (`docs/privacy.md` 5.3). Each device also sends an HMAC of what its screens show (D-116, `local/device-check.ts`), so two devices that show different numbers say so.                                                                                                                                     |
| Sessions                  | Theft or replay                                                                    | Random 256-bit token in an HttpOnly, Secure, SameSite=Strict `__Host-` cookie; the database stores only its SHA-256; 24-hour absolute expiry; "Sign out other devices" deletes the rows; signing in again on a browser deletes that browser's earlier session. Linking and repairing banks, removing a bank and passkey changes need a passkey check within 15 minutes. For a locked budget they, Delete account and a key change are also signed with the budget's key (`docs/privacy-keys.md` 11), so a stolen cookie alone can't do them. A session with no key can't write to the log.                                                                                                                                                                                                                |
| First sign-in             | Someone else registering first                                                     | The first passkey needs `SETUP_CODE` (a Worker secret, 32+ characters, constant-time compare), which stops working once an admin has a passkey (other users' passkeys don't reopen it; `docs/open-signup.md` 3.4). Added devices need a single-use 10-minute link from a signed-in device. WebAuthn challenges last 5 minutes in a signed cookie and are single-use (`used_challenge`, recorded in the same transaction as what they allow); origin, RP id and user verification are checked. A passkey added this way gets a sign-in, not the budget: it has no slot until a device that holds the key adds one (`docs/privacy.md` 5.8).                                                                                                                                                                 |
| Open sign-up (off, D-75)  | Scripted accounts, using up the free plan, a stranger as admin                     | Off until `SIGNUPS` is `open` and both Turnstile values are set; the Worker checks the switch, CSRF and Turnstile before any Durable Object request; per-IP rate limit, `MAX_USERS` and `SIGNUPS_PER_DAY`, re-checked in the same transaction that makes the account (`fence`); a sign-up is never an admin; other users can't link banks on Plaid Trial and share half of each daily limit (`store/shares.ts`). The robot check runs on its own address, so the app loads no outside script (D-113).                                                                                                                                                                                                                                                                                                     |
| Recovery key              | A leaked or guessed key; a thief who holds it                                      | 256 random bits made on the first device (no recovery codes, D-102), shown once and typed back before the budget is used. One half signs the recovery sign-in, so the server stores only a public key; the other half opens the recovery slot (`routes/recovery-key.ts`, `docs/privacy-keys.md` 4.2). Rate limited with sign-in. The admin has one too. Every device shows a notice for a passkey or recovery key another device added, and key changes from a recovery sign-in are held 7 days (D-89). Losing every passkey and the recovery key loses the budget: nobody can reset it (`docs/runbooks/restore.md`).                                                                                                                                                                                     |
| Ops endpoint              | Token leak                                                                         | `OPS_TOKEN` reaches only `GET /api/health` (statuses, no financial data); constant-time compare; kept in GitHub environment secrets.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| Plaid access tokens       | Leak from the database, logs or API                                                | AES-256-GCM with a Worker-secret key (`TOKEN_KEYS`) and per-row key version, bound to the link by its associated data (`packages/platform/src/token-crypto.ts`), in the server-only `bank_link` table under the Worker's stamp (`linkMac`); decrypted only in the fetch job and the link steps (`seal/fetch-job.ts`, `seal/link-watch.ts`); never returned by any endpoint; logs use an allowlist of fields. Accepted (`docs/privacy.md` 4.3): someone with the database and the Worker's secrets can ask Plaid for a link's data.                                                                                                                                                                                                                                                                        |
| Webhook endpoint (public) | Forged webhooks triggering work                                                    | ES256 `Plaid-Verification` JWT, key by `kid`, 5-minute `iat`, body SHA-256 (`packages/bank-provider/src/plaid.ts`); the handler only starts a fetch, or finishes a link being watched, for a known Item or link token                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| Browser session           | CSRF, clickjacking, script injection                                               | JSON content type + `x-ledgerline` header + same-origin `Origin` on mutations (sign-in routes included); SameSite=Strict cookies; CSP `script-src 'self' 'wasm-unsafe-eval'` with no outside host, since Plaid Link is hosted on Plaid's own site (`apps/web/public/_headers`, `docs/privacy.md` 5.7); `frame-ancestors 'none'`; `Referrer-Policy: no-referrer`; HSTS                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| App code                  | The server sending code that reads the keys                                        | A web app runs whatever its server sends (`docs/privacy.md` 4.2). The web build is reproducible and each release's file hashes are attested in public (D-96, `docs/runbooks/verify-build.md`); this covers the app's files, not the Worker, and can't catch code sent to one person once.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| Production Plaid keys     | Exposure to unreviewed code                                                        | GitHub `production` environment secrets, uploaded to the production Worker on each deploy (D-28); the environment isn't available to pull requests. There is no staging (D-36): tests and e2e use a fake Plaid or Sandbox values. The deploy token in the same environment could already read them through a deployed Worker, so this adds no new path                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| Plaid Items (10 for life) | Burning slots by mistake                                                           | Sandbox everywhere but production; update mode for repairs; Item meter and confirm step; server refuses a new link at 10                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| Bank data                 | Reading or tampering on the server                                                 | Each page is sealed to the budget's inbox key in the job step that fetched it, and the run is signed by the Worker (`seal/runs.ts`, `docs/privacy.md` 5.5); no readable page or bank log is kept (`raw_page` and `bank_event` were dropped, D-106). A device refuses a run sealed to any inbox key but the current one. Accepted (`docs/privacy.md` 4.1, 4.4): Plaid sees the data, it is in the Worker's memory until sealed, and a server with the Worker's secrets could sign false bank data.                                                                                                                                                                                                                                                                                                         |
| Copy on the device (D-45) | A stolen or borrowed device; a script in the page; a revoked device                | Kept on every device whose passkey gives PRF output (D-53), as one AES-GCM blob in IndexedDB whose data key is wrapped under HKDF(passkey PRF output ‖ a per-device share the Directory holds) (`apps/web/src/copy/vault.ts`); keys are non-extractable and in memory only; 10 idle minutes or 10 minutes in the background sign you out (D-57); wiped on sign-out, `not_member` or a revoked device; offline opening for 7 days after the last sign-in. Accepted (owner, D-45): someone with the passkey who keeps the device offline keeps the last copy; a script running while signed in reads what you can.                                                                                                                                                                                          |
| Data loss                 | Damage noticed late, or losing the Cloudflare account                              | No off-site backup, by the owner's choice (D-29), and the server can't restore a budget (D-102). The devices hold it, rebuilt from the newest checked snapshot and the entries since; the full backup is made on a device, after a passkey prompt, sealed with the recovery key by default, and kept yourself (`docs/runbooks/restore.md`). Accepted risk: losing the Cloudflare account and every device that holds the budget, with no backup.                                                                                                                                                                                                                                                                                                                                                          |
| Availability              | Daily free limits take the app offline                                             | Account-wide usage from GraphQL Analytics; the breaker pauses background work at 70%, refuses writes at 90% and rests at 95% (D-40), counting Durable Object and Worker requests too; past the Durable Object daily allowance the app says so plainly until 00:00 UTC                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| Supply chain              | Malicious dependency or action                                                     | Lockfile, Dependabot, OSV-Scanner, dependency review, actions pinned to commit SHAs, zizmor and actionlint                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |

Accepted: a compromise of your Cloudflare account exposes the secrets and the bank tokens, and lets the attacker serve changed app code that reads the keys the next time you open the app (`docs/privacy.md` 4.2); it doesn't expose the stored budget, which is sealed. A compromise of a device with your passkey (signed in) can open the budget. Hardware-key or passkey 2FA on Cloudflare, GitHub and Plaid is the main mitigation.
